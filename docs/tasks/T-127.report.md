What changed (only these two files; `families::exec` signature untouched)

Record fields written/read as cells (field names checked in `kit-meta/records/parties.toml`):
- `party_set_faction` writes `faction`; `store_faction_of_party` reads it back.
- `party_get_template_id` reads `party_template`.
- `party_set_flags` read-modify-writes `party_flags` (`<clear_or_set>` 0 clears the given bits, else sets them).
- `party_set_banner_icon` sets the low byte of `party_flags` (`pf_icon_mask`, header_parties.py:13) to the icon id.
- `party_set_ai_behavior` writes the low byte of `ai_behavior` (`ai_bhvr_*` mask 0xFF, parties.toml:103); `party_set_ai_object` writes `ai_target`.
- `spawn_around_party`: new party index = `m.party_count`, then `m.party_count += 1`; `party_template` from the operand and `faction` from the party template record's `faction`; the new id goes into `reg0` as the op comment says (header_operations.py:476). Where the party appears is not recorded (random around the source).

Members/stacks (text field `stacks`, parsed):
- `party_get_num_companions` = sum of the companion stack counts; `party_stack_get_troop_id` = troop of companion stack `stack_no`. Stacks whose flags have `pmf_is_prisoner` (header_parties.py:48) count as prisoners and are left out, as Native keeps companion and prisoner stacks apart.
- `party_add_members` / `party_remove_members`: the party's `stacks` cell is written unknown (only the engine knows the new list) and `reg0` (number actually added/removed, bounded by capacity) is unknown.
- `party_add_leader`, `party_add_template`, `party_upgrade_with_xp`: `stacks` written unknown (engine picks the stacks).

Counting/distance:
- `store_num_parties_of_template`: counts the run's parties whose `party_template` cell equals the operand; unknown if any party's template is unknown.
- `store_distance_to_party_from_party`: computed only when both parties are static (`pf_is_static`, header_parties.py:16) with record coordinates; otherwise unknown.

Known but no cell (modelled, so they stop being noise in `unknown_ops`): `party_set_name` (name is text, no numeric cell), and `set_spawn_radius`, `party_set_ai_initiative`, `party_set_ai_target_position`, `party_set_ai_patrol_radius`, `party_ignore_player`, `party_set_bandit_attraction`, `party_set_helpfulness`, `party_set_ignore_with_player_party` (run-time engine state the records do not hold).

Left unknown on purpose (still counted by core, one-line reasons):
- `party_get_position` — it fills a position register; the machine has no position registers, and a mobile party's position is whatever AI movement made it, not a record value.
- `party_get_current_terrain` — terrain comes from the map's terrain map at the party's position, not from any record.
- `remove_party` — frees/removes an id in the engine list; the run does not track removals (a comment in `party_is_active` says so).
- Any of the modelled ops whose party operand is unknown (e.g. `reg0` after an upgrade) is counted as `<op> (unknown party)` and changes nothing.
