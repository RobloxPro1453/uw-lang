# T-127: uw_start: party operations

Status: ready
Budget: $3.00
Steps: 300

## Goal

The dry run models the party operations Native's game_start uses, so the start snapshot knows which faction, template and members each party has.

## Known facts

- Crate `crates/uw_start` runs Native's `script_game_start` without the game (read src/lib.rs top
  comment and src/families/mod.rs rules). Families read operands with `m.get`, store with `m.set`,
  read record cells with `m.read(Cell::field(table, index, "field"))` / `Cell::slot`, write with
  `m.write`, build results with `Val::derived(n, &[inputs])`, and record start values come from
  `m.initial_field_text(table, index, field)` (the field text `uw new` prints; field names are in
  `kit-meta/records/<table>.toml`).
- The kit and sample mods are git-ignored; read-only copies are inside your worktree:
  `target/ref/kit/` (= `Module_system 1.171/`). Operation meanings: `target/ref/kit/header_operations.py`
  (each op has a comment). The built atlas is `target/uw-staging/atlas.json`.
- Unit-test style to copy: `crates/uw_start/tests/flow.rs` (tiny hand-made atlas, ops by name).
- The real run (`cargo test --release -p uw_start -- --ignored --nocapture`) prints the unmodelled
  operations; do NOT run it in debug (too slow).
- Never guess an operation's effect: if the engine computes something the records do not hold
  (positions after AI movement, wages …), leave it unknown.
## Steps

Implement in `crates/uw_start/src/families/party.rs` only (keep `families::exec` signature). Unmodelled counts from the real run: store_faction_of_party 1,024,281; party_get_template_id 252,000; store_distance_to_party_from_party 79,420; party_get_num_companions 940; party_stack_get_troop_id 825; party_upgrade_with_xp 460; party_add_template 440; party_set_faction 340; party_set_banner_icon 230; party_is_active 226; spawn_around_party 183; set_spawn_radius 176; store_num_parties_of_template 80; party_get_current_terrain 60; party_get_position 60; remove_party 60; party_set_name 26; party_add_leader 25; party_add_members; party_remove_members; party_set_flags; party_set_ai_*; party_set_slot is already core.
- party faction = cell `Cell::field("parties", p, "faction")` (start value from the record; check the field name in kit-meta/records/parties.toml). `party_set_faction` writes it.
- spawn_around_party creates a new party: index `m.party_count`, then `m.party_count += 1`; its template/faction come from the party template record (party_templates.toml); store the new id in reg0 as the op comment says.
- Distances: only when both parties are static Native parties with known positions (record field); else unknown. Check the engine unit in header_operations comment.
- Members/stacks: model from the record's member list where the op only reads; mark unknown where the game would have changed them.

## How to test

- Unit tests in crates/uw_start/tests/party_t127.rs on a tiny atlas (copy flow.rs helpers) with a parties table: set/read faction, spawn increments count and returns id, distance between two static parties, unknown position stays unknown. Each test fails if the op is not modelled (assert the op is absent from `m.report.unknown_ops`).

## Done when

- Every operation listed in Steps is modelled or explicitly left unknown with a one-line reason in the report.
- Build and tests pass.

## Do not

- Only edit src/families/party.rs and the new test file (plus Cargo.toml dev-deps if needed). Do not touch src/lib.rs.

## Stop and report if

- An operation's meaning cannot be found in header_operations.py.
- A test still fails after 5 steps on it.
