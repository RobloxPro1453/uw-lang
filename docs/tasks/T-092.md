# T-092: New troop from an existing one: `troop elite_crossbowman like swadian_crossbowman { }` (easy-language §3)

Status: ready
Budget: $2.00
Steps: 450

## Goal

In a `uw build` mod folder:

```
troop elite_crossbowman like swadian_crossbowman {
    name "Elite Crossbowman"
    level 22
    agility 18
}
```
makes a new troop: a copy of the Native one with these fields changed, appended at the end of the troop
list (Native troops keep their numbers). Code can then use `elite_crossbowman` (trp_elite_crossbowman).

## Known facts

- Troop record fields and their names: kit-meta/records/troops.toml (T-075 full names; attributes part has
  `strength agility intelligence charisma level`). Value read/print: crates/uw_decomp/src/records.rs.
- Game names (`swadian_crossbowman`) resolve through `Atlas::resolve_ref` once names are installed (uw build does).
- How a mod folder adds things to Native lists: uw_runtime + crates/uw_emit (see `new menu_…`).

## Steps

1. Syntax: `troop <new_id> like <existing> { <field> <value> … }` with the record text field syntax.
2. Build: start from the atlas value of `<existing>`, apply the fields through the troops schema, emit one
   append to `troops` (uw_runtime). `<new_id>` must be new (error if it exists). Its references in code
   (`trp_<new_id>` and `<new_id>`) resolve (add it to the atlas view used by the check).
3. Golden crates/uw_cli/tests/golden/troop_like/ (fixture atlas; add one troop and the troops schema use).

## How to test

The golden fails if the appended tuple differs from the expected copy-with-changes.

## Done when

- Build and tests pass; existing goldens unchanged.

## Do not

- Touch crates/uw_decomp/src/project/**, lib/**, kit-meta/**.

## Stop and report if

- uw_runtime cannot append to troops without changing the staging chain (describe it). 5 failed steps.
