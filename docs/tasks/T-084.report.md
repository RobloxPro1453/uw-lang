What I verified (all in crates/uw_check/src/lib.rs):
- The only public entry points are `min_args` (:135), `check` (:1343) and `check_block` (:1785). `Ctx` (:176-197), `FnDef` (:161-168), `inline` (:306-355) and `substituted_stmt` are private, so uw_cli cannot build a checker or inject fns.
- `check_block` (:1785-1806) hard-codes `let fns = BTreeMap::new()` (:1786), `sources: &[]` (:1795) and `native: true` (:1793). With an empty fn map `inline` (:306-309) returns `Vec::new()` for every call, so `give_gold(1000)` can never be expanded to `troop_add_gold`; and even if fns were passed, `inline` reads bodies through `stmts_in` (:210-219), which indexes `self.sources[def.file]`, so the fn sources must live inside the checker — there is no public way to put them there.
- Reusing `check` instead is not viable: it runs with `native: false` (:1392), so it rejects flagged Native names like `neg|this_or_next|eq` (:968-985) and enforces header arg counts (:992-1007). Project record blocks are Native text, so routing compile through `check` would break existing project builds, which the spec forbids.

2. It collects fns from `fn_sources` exactly like `check` does at :1351-1383 (same E0214 fn-has-an-op-name and E0202 duplicate diagnostics, `origin_in` origin).
3. It builds a local `sources` vec of length `fn_sources.len() + 1`: index 0 is `Source { file: file.clone(), tree: File { module: None, items: vec![] } }`, then the fn sources shifted by one, so `FnDef.file` indices match (`SourceFile` is `Clone`, crates/uw_diag/src/lib.rs:24-25; `File` fields are pub, crates/uw_syntax/src/lib.rs:39-43).

5. Note for the caller: `check_block` returns `Vec<Diagnostic>` and drops `Error.file`, so a diag raised inside an inlined fn body has a span into the fn source.
