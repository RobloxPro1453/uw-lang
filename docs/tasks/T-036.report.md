The core bug (not fixed, per spec)
`record_id` (records.rs:147-151) is `entry.id.or(entry.name)`, and for skins the dump leaves both null (py/atlas_dump.py:57 has `id_file = None`, and dump_table sets `name`/`id` to null then — py/atlas_dump.py:203-204,240). So every skin prints as `skin  {` with an empty id, and `parse` rejects it at records.rs:237-239 ("line 1: expected the record id"); `TableReport::first_failures` shows two entries of exactly that message. A skins schema cannot work around this: the id is printed by the core, not the schema. The minimal core fix is a fallback to the record's first value when it is a non-empty string (skins' field 1 is the skin name, "man"/"woman"), i.e. id = `entry.id` → `entry.name` → `value[0]` when it is a str/ident. With id_prefix `""`, `strip_prefix` then leaves the name unchanged.
