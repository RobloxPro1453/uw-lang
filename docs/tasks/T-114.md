# T-114: Words as conditions (`if player.has(iron_shield)`) and `say "…"` without parentheses

Status: ready
Budget: $1.50
Steps: 400

## Goal

The easy-language example (docs/arsiv/meclis-yon1-yon2/kolay-dil-taslak.md §5) compiles as written:

```
on enter mountain_road when time.hour >= 12 {
    if player.has(iron_shield) {
        player.remove(iron_shield)
        say "Bandits took your shield!"
    }
}
```

## Known facts

- Words are `fn` in lib/core.uw (and a project's fns/); `player.gold.get(:out)` style getters feed
  comparisons (T-082/T-083 object words, uw_check). T-109 (area/on enter) found that a fn call is not accepted
  as an `if`/`when` condition and that `say` needs parentheses.
- Native conditions are operations that fail/succeed (e.g. `troop_has_item_equipped`, `store_item_kind_count`
  + `ge`). Verify every operation name in the atlas/kit; never invent one.
- Design (decided): a **condition word** is a `fn` whose name the library marks as a test, written
  `fn player.has?(:item) { … }` OR `test fn player.has(:item) { … }` — pick the one that fits the parser with
  the smaller change and say which in the report. Its body may contain only condition operations; the checker
  rejects anything else with a Turkish error. Used as a condition (`if`, `when`, `and/or/not`) it is inlined
  like other words. `not player.has(x)` must work (Native: wrap with the existing `neg|`/try pattern the
  checker already uses for `not`).
- `say "text"` = `say("text")`: a statement-level shorthand for one-argument words whose argument is a
  string literal; keep it narrow (only when the next token on the same line is a string).
