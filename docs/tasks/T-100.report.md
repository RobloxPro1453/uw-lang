Blocked on the spec's own stop condition: a `uw create` project's errors carry no file/line, so `uw check --json` cannot honestly fill line/column/code for them. I made no code changes (working tree is clean); I stopped and am reporting where the information is lost, as instructed.

What I verified (read-only)

Mod-folder half is fine and implementable:
- crates/uw_cli/src/build.rs:29-85 is exactly parse+check; uw_check::Error carries `file` (index into sources) plus a real `uw_diag::Diagnostic` with code/message/span/help (crates/uw_check/src/lib.rs:60-62), and the entries are absolute `PathBuf`s, so file/line/column/end_column/code/help for JSON are all available. `parse_sources` (build.rs:264-291) only needs to hand back the diagnostic instead of printing it, to keep `uw build`'s stderr identical.

Project half cannot carry a position — that is the blocker:
- uw_decomp::project::load returns `Vec<String>` (crates/uw_decomp/src/project/load.rs:56-61); every error is built by `format!` with no span: load.rs:85 (read error), :94 (unknown record kind), :102 (record parse error), :135/:167/:174 (lock/duplicate-id problems). uw_decomp has no Diagnostic/Span type at all on this path (grep: no Diagnostic, no line_col in crates/uw_decomp/src).
- The record text is split by `split_records` (crates/uw_decomp/src/project/mod.rs:168-191), which returns `Vec<String>` and throws away where each record started. So the "line N" inside a record parse error (crates/uw_decomp/src/records.rs:557-560, 570, 574, 585, 596) is counted from 1 at the record's own first line (Parser::new sets `line: 1`, records.rs:838-840) — not the line in the project file. There is no column anywhere and no error code.
- The mistakes a project usually has are inside `ops { … }` blocks, and those positions are dropped twice: crates/uw_cli/src/roundtrip.rs:188-192 builds a fake `SourceFile::new("block.uw", text)` and then `one_line` keeps only the line containing "error", discarding the `--> block.uw:3:4` line that `Diagnostic::render` produced (crates/uw_diag/src/lib.rs:86-94). All that reaches the user is `"<project file>: error[E0201]: unknown name `x`"`.
- build_project.rs:485-497 prints those strings as they are; nothing in the pipeline keeps a byte offset or a span that `uw check` could convert to line/column.

So for a project the JSON object would have a real `file` (as a path inside the message text) but a fabricated `line`/`column` (worst case 1:1) and no reliable `code`. Scoring the spec's format that way would be guessing, which the rules forbid.

Why I did not "just fix it": making project errors carry spans means changing uw_decomp (split_records returning byte offsets, records::parse_record returning a structured error, uw_cli::roundtrip::compile_with returning the Diagnostic instead of one flattened line) and new plumbing through build_project — a redesign the spec explicitly tells me to stop before, not a surgical change. crates/uw_syntax, crates/uw_check, lib/** and editors/** (also forbidden) are not the problem here; uw_decomp and the uw_cli roundtrip helper are.

2. Let `roundtrip::compile_with` return the first `uw_diag::Diagnostic` plus its SourceFile instead of a flattened String, so a block error in a project file keeps its position (its own SourceFile is the record's `ops` body, so the offset needs shifting by the block's offset in the file).
3. Then `uw check` for projects is a straight mapping to the spec's JSON, the same as the folder half — which needs only the refactor of build.rs:29-85 plus the `check` subcommand and the two tests from step 3.
