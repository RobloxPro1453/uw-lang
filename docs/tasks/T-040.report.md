The core bug (not fixed, as the spec says)
- `records::print` writes the record id bare (`format!("{} {} {{", schema.kind, record_id(schema, entry))`), while 17 Native string identifiers contain `=` (ID_strings.py:1901, 1930, 1990, 2048, 2257, 2282, 2395, 2539, 2568, 2595, 2596, 2637, 2715, 2718, 2737, 2738, 2878), e.g. `str_test_effective_relation_=_reg3`.
- The parser's `word()` stops at `=`, so parsing its own output fails at line 1: first failures reported by the test are e.g. `updating_faction_notes_for_s14_temp_=_reg4: line 1: expected `{` after `string updating_faction_notes_for_s14_temp_``. The 17 failures equal the 17 `=` ids exactly, so all other string records are fine.
- No schema can fix this: the id text is fixed by the kit and `id_prefix` cannot remove an `=` in the middle. The fix belongs in the core: print the id quoted (escaped) when it is not a word-parseable token; `parse` already accepts a quoted id at records.rs:232. I did not touch `records.rs`, as the spec forbids it.
